# 工程约定

## 路由

- `/` 首页
- `/blog` 文章列表
- `/blog/[slug]` 文章详情
- `/beijing-bars` 北京酒吧指南
- `/bars/[slug]` 酒吧详情
- `/about` 关于我们
- `/preview` 开发模板索引
- `/api/health` 无敏感配置的健康检查

## 数据边界

页面和组件只能通过 content repository 读取内容，不直接调用 Notion 或数据库。文章通过稳定的 barIds 关联酒吧，Slug 只负责对外网址。每家酒吧资料维护一份，文章可关联多家。

当前内存适配器用于小量演示数据。数据增长后，将查询条件、排序和游标分页下推到数据库；不得把整个酒吧数据库或完整文章正文发送到目录客户端。BarDirectory 当前的客户端筛选只适合这些演示数据。

建议后续分为 venues、articles、article_venues、assets；采集另设 source_records 与 import_jobs。原始采集记录不能直接覆盖人工编辑内容。用来源 ID、规范化地址等做去重，保留来源、采集时间与核实状态，人工确认后才进入公开内容。

Notion 是否作为编辑入口可后续决定，数据库只保存规范化的发布快照；页面模板无需随来源改变。未来大规模数据库的实际选型，以查询、数据量和部署约束决定，不预先绑定 D1 或 PostgreSQL。

## 发布与内容安全

公开读取函数只返回 published 记录。演示记录有 demo 标志，在 UI 中明确显示、不进入 sitemap。真实发布流程要增加必填校验、稳定图片存储、草稿隔离、快照和回退。不要把 Notion 临时图片 URL 当作永久资源。

改页面不修改原始内容。内容更新不要求编辑页面 JSX。两人可共同改接口，但应同步更新类型与检查。

## 环境

本地 dev 已具备，远程 staging 尚未创建。正式域名仍服务先前预告页，未经确认不要用虚构内容替换。测试站、数据库和密钥与生产隔离；robots/noindex 不代替访问控制。

当前 Sites 负责托管和实际 Cloudflare 资源绑定。后续迁移到自有 Cloudflare 或其他平台应单独实施，避免直接手改 Sites 代管的配置。

## 首个工具

将来增加 `/tools/[slug]` 与有针对性的服务端接口。付费生成请求在服务端执行，配置限流、费用上限、超时与任务状态；目前不创建空壳写接口、不假装登录或生成已接通。
